# First vertical integration

1. Generate JSONL with `ARMOR-SIMULATOR` (`--server-url` and `--ingest-token` deliver it over HTTP).
2. Validate every envelope with `ARMOR-COMMON` (`--validate`); the server validates again at its boundary.
3. Read the state from `GET /api/v1/status` and the changes from `GET /api/v1/history`.

`tests/vertical-slice.test.ts` runs exactly this path with the real simulator and the real server.
The Node service provides `GET /healthz` and `GET /api/v1/status`. It accepts no
unauthenticated writes.

Alarms leave the server on MQTT `armor/server/alert` and, when `ARMOR_ALERT_WEBHOOK_URL` is set, as a
JSON POST. When `ARMOR_ALERT_WEBHOOK_SECRET` is set the body is signed: check
`X-Armor-Signature: sha256=<hex HMAC-SHA256 of the raw body>` in constant time before trusting it. The server has TLS of its own (`TLS_CERT_PATH` and
`TLS_KEY_PATH`), authentication by session or token, four roles, rate limits and an audit trail; keep it behind them when you expose it.

When `ARMOR_MQTT_URL` is explicitly configured, the Node server subscribes to
`armor/node/+/telemetry` and `armor/node/+/health` at QoS 1 (a health message with `"kind":"panel"` comes from a wall panel and is kept apart from the radars). Invalid JSON,
unknown topic families and malformed payloads are rejected before reaching the
state projection. The broker credential is read only from the process environment.
The link to the broker can be encrypted (optional, off by default): with an `mqtts://` address in `ARMOR_MQTT_URL` and `ARMOR_MQTT_CA_FILE` naming the certificate of the installation's own authority (one PEM file), the server trusts that authority only and the certificate of the broker must vouch for the name or address in the URL. The server refuses to start if the file is not one valid certificate or if it is set with an `mqtt://` address. `GET /api/v1/system/connection` (administrator) answers `mqtt_tls`: whether the link is encrypted and the name, fingerprint and end date of the pinned authority.

The server also subscribes to `armor/solar/+/+/state` and `armor/electrical/+/state` (QoS 1), the messages of the solar gateway nodes and of the electrical nodes, and accepts the same messages over `POST /api/v1/solar` and `POST /api/v1/electrical/readings` with the ingest token. Over MQTT the `node_id` in a body must be the node of its topic. An operator reads them with `GET /api/v1/solar` and `GET /api/v1/electrical/readings` (with their `/history`); the Electrical Designer's drawing is kept at `GET`/`PUT /api/v1/electrical/design`. The broker's ACL for `armor-server` needs `topic read armor/solar/#` and `topic read armor/electrical/#`.

|---|---|---|

| `armor/solar/+/+/state` | read | solar gateway nodes |
| `armor/electrical/+/state`, `armor/electrical/+/result` | read | electrical nodes |

| `armor/network/+/state` | read | ARMOR-NETWORK nodes |

| `armor/server/alert` | write | every alarm that is not silent |

| `armor/alarm/<node>/zigbee` | write | the state of the Zigbee zones of a panel; with the setting `server.zone_feed` off nothing is written, and with `server.zone_feed_signature` on every message carries `seq` and `sig` (HMAC-SHA256 with the key of the panel, `GET /api/v1/alarm/zone-feed/key/{node}`) |
| `armor/alarm/<node>/state` | write | only with the setting `server.alarm_state_signature` on (off by default): a copy of each state heard from a panel, with `seq` and `sig` added (HMAC-SHA256 with the key of the installation, the file `alarm-state.key` of the data directory or `ARMOR_ALARM_STATE_KEY_FILE`); the server ignores its own copy when it hears it again |
| `armor/alarm/<node>/policy` | write | the security options that concern a panel (`config_hash`, `zone_feed`, `zone_feed_signature` and, when it is not `if_set`, `disarm_pin`), every 30 seconds and when an administrator changes one |

| `armor/solar/<node>/maintenance/command` | write | only with `ARMOR_BATTERY_WRITE=1` (an order to write to a Pylontech battery of a gateway node) |
| `armor/solar/+/maintenance/result` | read | the gateway nodes' answers to those orders |
| the command topics of the devices registered | write | a plug, a light |
| `homeassistant/#` | write | only with `ARMOR_HA_DISCOVERY=1` |

The broker's access list must give the server's account exactly that and nothing more (see ARMOR-DEVOPS). The topics of the nodes, of the server and of Home Assistant
(`armor/` except `armor/device/`, and `homeassistant/`) cannot be used as the state or command topic of a device: otherwise anyone who may create a device could make the
server publish a command to a panel. A **silent** alarm (a disarm with the duress PIN) is never put on `armor/server/alert`; it goes only to the webhook, Telegram and ntfy.
Commands to panels and switches are off unless the installation turns them on, and each one is checked and audited (see `docs/NODE_FIRMWARE.md` for what a node does with it).

A wall panel acknowledges the alarms with `POST /api/v1/alarms/acknowledge`. The acknowledgement of a panel's account proves nobody is standing there, so it stays unverified and a critical alarm keeps being escalated; if the body carries `pin` (the PIN of that account, set by an administrator like any user's) and it is the right one, the acknowledgement counts as a person's. A wrong PIN is refused (403) and acknowledges nothing, repeated wrong ones lock the PIN (429, the same lockout as a disarm), and the duress PIN acknowledges without verifying. A panel cannot acknowledge a single alarm.

## The panel's live channel

`/api/v1/panel/events` is a WebSocket for the wall panel (ARMOR-NODE-HMI), so it does not have to ask `GET /api/v1/panel/summary` every few seconds. It is admitted with the session cookie of a panel, operator or administrator account (never a viewer), from the server's own origin or one of the Studio origins, and only while `panel.live_events` is on. The server sends one text frame when the socket opens, one whenever the summary changes (looked at once a second, and at once when the state of the nodes changes) and the same summary again every `heartbeat_ms` (5000), so a quiet channel can be told from a dead one:

```
{"type":"summary","heartbeat_ms":5000,"summary":{ ...the document of GET /api/v1/panel/summary... }}
```

It carries nothing the panel cannot ask for and takes nothing: whatever the client sends closes the socket (1003), a client that falls 64 KB behind is dropped, and a session that ends closes it with 4401. The whole state of the installation stays on `/api/v1/events`, which a panel account may not open. Arming, disarming and acknowledging go through the same routes as before.

## Spoken turns

The wall panel sends one spoken turn to `POST /api/v1/voice/turn` (or `/api/v1/voice/v1/turn`) with the voice token in `X-Armor-Voice-Token`; the server passes the audio to the voice gateway on this machine (raw 16 kHz 16-bit mono PCM, the language and the silence policy in headers, as always). There are two forms of request, told apart by the `Content-Type`:

A panel may say who it is with `X-Armor-Panel` (its node id, lowercase letters, digits, `_` and `-`; anything else is ignored): the server passes it on to the gateway, writes it in the audit trail of the turn, and when the gateway carries out a command with the operator token and gives the same header back, the command is written as `operator via <panel>` and the confirmation the gateway issues is bound to `panel:<id>`, so two panels behind one address do not share a pending question. A person signed in with a session of their own is never replaced by the header.

* **Raw** (`audio/L16;rate=16000`): the whole body is the audio and the language is in `X-Armor-Language`. The answer is the gateway's JSON, `{heard, reply, audio?}` with the audio in base64. Unchanged.
* **Binary** (`multipart/form-data`, ARMOR-COMMON's contract *Voice turn*): the part `audio` carries the same PCM as raw bytes and the optional part `meta` (`voice_turn_meta`) the language and what the panel wants back, `reply_audio`: `base64` (the default: the gateway's JSON), `binary` (`multipart/mixed` with the parts `result` and `audio`, 33 percent smaller and with nothing to decode) or `none` (JSON without audio). Anything else in the request is refused: `400 bad_multipart`, `411 bad audio length`, `413 audio_too_large`, `415 unsupported_audio_type`, `422 unknown_part`, `duplicate_part`, `missing_audio` or `bad_meta`. The token is checked before the body is read.

The sizes are settings of the server, `voice.turn_max_bytes` (the audio of a turn, in both forms; 480000 bytes, 15 seconds, by default; 3200 to 1920000) and `voice.reply_audio_max_bytes` (the spoken answer handed back in the binary form, 200000 by default; 3200 to 1000000; both are edited in Studio and start at the values of `ARMOR_VOICE_TURN_MAX_BYTES` and `ARMOR_VOICE_REPLY_AUDIO_MAX_BYTES`; a longer one is left out, the result says `audio_omitted: "too_large"` and the text still goes). The texts `heard` and `reply` of a binary answer are cut at 2000 characters. A gateway that answers something that is not a voice reply gets `502 voice_bad_reply` in the binary form. The panel (ARMOR-NODE-HMI) still sends the raw request; the voice gateway needs no change to be used with the binary one, because the form is between the panel and this server.

The Android and iOS apps are optional clients of the same route. In both, a switch in the settings of the Assistant is off by default; while it is off the microphone is never opened, the permission is never asked and nothing is sent. Turned on, the app records one short turn (cut at ten seconds), sends it as the raw request with the voice token in `X-Armor-Voice-Token` (not the session of the person) and reads the answer; a refusal of the server is shown by its code. When the silence confirmation is `challenge`, the app shows the number of the answer on its screen. The voice token is kept sealed on the phone.

Panel side, pending: the firmware of the alarm panel does not yet read the policy, check the signature or store a hash of its configuration with its saved state; until it does, those three settings are published and signed but nothing on the panel acts on them.

## The sound of an alarm

Two things the wall panel can play when an alarm arrives, each behind its own option of the security settings (Studio, Configuration > Security) and both off by default. In both the panel asks with its own session (the `panel` account may call these reads and nothing else of the family), checks the size and the SHA-256 it is given (`X-Armor-Audio-Sha256`, also the ETag, so a panel that holds the same samples gets `304`), and plays its own tone if it gets nothing.

* **Said out loud**: `GET /api/v1/alarm-audio/spoken?language=&source=&severity=&code=`. The sentence is never free text: it is built from the origin (`device`, `solar`, `electrical`, `network`, `alarm`, `other`), the severity (`critical`, `high`, `warning`, `info`) and the words of the alarm code in the language asked (the table of the alarm codes, in the eight languages; a code the server does not know is not read out). The voice gateway says it (`POST /v1/speak` of ARMOR-VOICE-AI, which needs a text-to-speech engine) and the server keeps the result in a cache of 64 sentences and 8 MB, so the speech engine is asked once for each different sentence. The answer is raw 16 kHz 16-bit mono PCM (`audio/L16;rate=16000`), at most `voice.reply_audio_max_bytes`. Without a gateway it is `503 voice_unavailable`, without a speech engine `503 tts_unavailable`.
* **Own sounds**: an administrator uploads one sound per origin with `PUT /api/v1/alarm-audio/sounds/{source}` (a WAVE file of 16 kHz, 16-bit, mono PCM; from outside the house it asks for the proof of identity again) and takes it away with `DELETE`; the panel reads it with `GET` (raw PCM as above). The file is parsed byte by byte and refused unless it is exactly that format, at least a tenth of a second long, not longer than `ARMOR_ALARM_SOUND_MAX_BYTES` (128000 bytes, 4 seconds, by default; up to 256000) and not silence; only its samples are kept, in `alarm-sounds/` of the data folder, together with their hash (a file that no longer matches it is not served). Every upload and removal is in the audit trail.

`GET /api/v1/alarm-audio` tells Studio what is on, whether a gateway is set up, the limits and the sounds stored.

## The summary of a day and the heat map

Two reads for administrators and operators, each behind its own option of the security settings (Studio, Configuration > Security) and both off by default; with its option off a route answers `404` whoever asks. A viewer, a wall panel and a service with its own token are refused (`403` or `401`) before anything is read. Neither Python project listens on a port: the server runs each as a command, one at a time, with a time limit, an environment that holds nothing of the server's secrets and arguments no shell reads, and it never passes on what the command says on its error output.

* **The summary of a day**: `GET /api/v1/summary/daily?date=YYYY-MM-DD&lang=xx` (`date` defaults to today in the time zone of the installation, `lang` to the language of the alerts). ARMOR-SERVER-AI turns the alarms the server kept for that day into counts, the serious alarms, patterns with the events that show them and a readable text in one of the eight languages. Only the code, severity, zone and node of an alarm reach it (never its detail or text, and never a silent alarm). It needs `ARMOR_PYTHON`, `ARMOR_DAILY_SUMMARY_AI_DIR` and `ARMOR_DAILY_SUMMARY_CONFIG`, and the settings file must say `"enabled": true` too (`503 daily_summary_not_configured`, `503 daily_summary_off_in_settings`). It covers the alarms the server keeps (the most recent ones) and, from them, the links that were lost (a node, camera, device or other equipment that went silent, as `node_link_lost` with how long it lasted) and the false alarms (an intrusion alarm that a disarm ended within `summary.false_alarm_s`); and, from the daily log (`daily-log.json` in the data directory, written atomically, mode 0600, only while the option is on), the readings of the sensors (the fields on `ARMOR_DAILY_LOG_SENSORS`, at most one every `summary.reading_every_s` per sensor) and the power of the house (the main meter, or the largest AC channel, at most one every `summary.power_every_s`). The log keeps `summary.log_days` days, at most `ARMOR_DAILY_LOG_MAX_EVENTS` events a day and `ARMOR_DAILY_LOG_MAX_BYTES` bytes, the oldest day going first. Only plain identifiers, codes, severities and numbers reach the AI: never a name, a text, an address or a field that is not on the list. It raises no alarm. `422` for a date that is not a day or a language outside the eight, `502 daily_summary_failed` when the command fails or prints something that is not a report.
* **A false alarm**: `POST /api/v1/alarms/:id/false-alarm` with `{ "false_alarm": true }` (the default), `false` or `null` (take the mark back) lets an administrator or an operator say that an alarm was a false alarm; a viewer and a wall panel's account are refused (`403`), a silent alarm does not exist for an operator (`404`), and each change is in the audit trail (`alarm.false_alarm`). The alarm keeps `false_alarm` and `false_alarm_by`, and the summary of a day counts the mark before it infers anything from a disarm.
* **The heat map**: `GET /api/v1/vision/heatmap?camera=&format=json|png|svg&scale=1..64`. ARMOR-VISION counts activity per cell of a grid over the scene (positions only, never a picture, and the JSON says `contains_images: false`, which the server checks before it answers). The map is asked of the live service (`python -m armor_vision serve`), which keeps the activity engine in memory, takes the detections as they happen (`POST /ingest`, from a camera pipeline or a simulator) and serves the map; this server does one GET to the address in `vision.service_url` (`ARMOR_VISION_SERVICE_URL` is where it starts) and sends nothing of its own in it: no cookie and no credential of the server; the only header is the optional token of the vision service (`ARMOR_VISION_SERVICE_TOKEN` or its file), which goes to that service alone. `503 heatmap_not_configured` when the address is empty or not valid, or is not this machine while `vision.service_remote` is off (the request never leaves), `502 heatmap_failed` when the service cannot be reached in time or answers something that is not a map, `404 unknown_camera` or `404 heatmap_pipeline_off`, `400 invalid_query` for any other parameter or value. The map is the one the service holds at the moment of the request.

* **The crossings of the counting lines**: `GET /api/v1/vision/counts` (no parameters; the same option, `vision.heatmap`, and the same people as the heat map) gives `{ "cameras": { camera: { line: { "to_left": n, "to_right": n } } } }`: how many times each counting line of each camera has been crossed in each direction since the live service of ARMOR-VISION started. The server accepts nothing but those whole numbers from the service (a name that is not plain, an extra field or a count that is not a whole number makes it `502`), and every ask is written in the audit trail. Studio shows the counts next to the lines in Configuration > Cameras.
* **The events of the vision service**: `POST /api/v1/ai/vision-events` (the token of the observation service, nothing else opens it) takes the event `armor.vision.event/v1` or `v2` of ARMOR-VISION: the camera, the zone and its kind, the followed object and its box, `authorizes_action` (always `false`; `true` is refused), `radar_tracks` and the optional `vectors` (where each followed object was heading). A zone of kind `alert` raises an alarm (`camera_motion`, `high`, with the zone, the label, the confidence, the radar tracks and the heading) only while the system is armed and once until it is closed, and the evidence picture is taken at once; a zone of kind `detection` is only written in the audit trail (`{ raised: false, reason: recorded }`). `422 invalid_vision_event`, `404 unknown_camera`.
* **The activity events of the vision service**: `POST /api/v1/ai/activity-events` (the token of the observation service, nothing else opens it) takes the event `armor.vision.activity/v1` of the activity engine of ARMOR-VISION: `zone_enter`, `dwell`, `loiter` and `zone_exit` name their zone, `line_cross` names its line and direction; `authorizes_action` is always `false`, a field the contract does not name is refused. Every event is written in the audit trail. An entry, a stay or a loitering in a zone of kind `alert` raises the same alarm as a vision event (`camera_motion`, `high`) only while the system is armed and only when the event does not carry `notify: false`; the vision service sets that flag on the events of a zone whose profile of the arming mode says the people the alarms go to are not told (`{ raised: false, reason: notify_off }`: still recorded). A `detection` zone, a zone the server does not know, an exit and a line crossing are only recorded (`reason: recorded`). The route takes them only while the option `vision.activity_events` is on (off by default: `{ raised: false, reason: feature_off }`), and the vision service sends them only when its settings carry a `delivery` (off by default). `422 invalid_activity_event`, `404 unknown_camera`.

## Headers of the API

Every answer under `/api/` carries `Cache-Control: no-store`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`; with a certificate of its own the server also sends a short `Strict-Transport-Security`. The panel of a node, passed on through `/api/v1/nodes/{id}/panel/`, keeps the headers of its own page.

## Alarms to Telegram and Home Assistant

Besides MQTT and the signed webhook, an alarm can be sent to a Telegram chat and to Home Assistant. They are set up in the settings file of the server (Studio >
Configuration > Settings files > `armor.env`, then restart the server) and tried from Studio > Configuration > Notifications, which sends a test message and says what
each place answered. The sentences are told in `ARMOR_ALERT_LANGUAGE` (`en`, `es`, `de`, `fr`, `it`, `ja`, `zh` or `pt`; `es` when it is not set). `GET /api/v1/admin/notifications` also gives `metrics`: for each place that has been sent something, the messages delivered, failed (after the retries), dropped from a full queue and waiting, and when and why the last one failed (no message and no address is in it).

**Telegram.** 1. In Telegram, talk to `@BotFather`, send `/newbot` and keep the token it gives (`123456789:AA...`). 2. Open a chat with your new bot (or add it to a group) and
send it any message. 3. Open `https://api.telegram.org/bot<TOKEN>/getUpdates` in a browser and read `"chat":{"id":...}` (a group's id is negative). 4. Put in `armor.env`:

    ARMOR_TELEGRAM_BOT_TOKEN=123456789:AA...
    ARMOR_TELEGRAM_CHAT_IDS=123456789,-1001234567890

One message goes to every chat of the list. The server reaches `api.telegram.org` over HTTPS, so the machine needs a route to the Internet; the token is never written in the audit
trail or in an error.

**Home Assistant.** 1. In Home Assistant create an automation whose trigger is *Webhook*; copy the webhook id it shows (or choose one, 8 or more letters, digits, `-` and `_`).
2. Make its action what you want (a notification to the phone, a siren, a light), using the data of the call: `trigger.json.text` is the sentence for a person,
`trigger.json.title` is `A.R.M.O.R.`, and `trigger.json.event`, `node_id`, `severity`, `code`... say what happened. 3. Put in `armor.env`:

    ARMOR_HOMEASSISTANT_URL=http://192.168.0.20:8123
    ARMOR_HOMEASSISTANT_WEBHOOK_ID=armor-alerts-8f3a2c1d

The id is a secret (whoever has it can trigger the automation); the settings file shows it masked. Both places are tried again after 1, 4 and 15 seconds when they do not answer,
and every end - delivered or given up - is in the audit trail (`alert.telegram`, `alert.homeassistant`).

## Node health and arming profiles

Every setting the server reads is listed, with its limits and an example, in [ENVIRONMENT.md](ENVIRONMENT.md) (generated from the code).

Every route the server registers is listed, with who may call it and the file that registers it, in [ROUTES.md](ROUTES.md) (generated from the code, and checked by a test).


* A node may also leave a last will on `armor/health/<node>`: the broker publishes `{"node_id":"<node>","online":false}` (nothing else in the body) when the node's connection is lost without a goodbye. The server takes it as "this node went away" at once instead of waiting for the silence limit, and it never counts as a report. A body that names another node than the topic is refused like any other. The other half is the birth: each time a node connects it says `{"node_id":"<node>","online":true}` on the same topic (retained, like the will), which the server takes as "this node is here" and never as a report, so the last message of the topic is always the state of the node, also after the server restarts.
* **The copy of the node traffic (off by default)**: while the option `ingest.recording` is on (Studio, Configuration > Security, or `PUT /api/v1/system/ingest/recording` with `{ "enabled": true }` by an administrator, written in the audit trail; `GET` reads the state) the server appends each message it takes or refuses to `ingest-recording/ingest.jsonl` in its data directory, as `{"topic","payload","at","accepted","reason"}` per line, which `ARMOR-SIMULATOR --replay` plays again (`--replay-accepted-only` leaves out the refused ones). Messages over MQTT and the HTTP reports of the nodes (telemetry, health, and the alarm, electrical, solar, network and node-health reports) are copied, each under the topic of the broker that carries the same message, so the simulator plays them the same way; a refused HTTP report is copied when its body at least names its node. The orders to the nodes are not copied, and a field named like a secret is left out. `GET /api/v1/system/ingest/recording` also tells how many messages were taken and refused since the server started and lists the files with their sizes; `GET /api/v1/system/ingest/recording/file?index=N` (an administrator who proved themselves again if they came from outside) downloads one of them (0 is the file being written, 1 the one before it) only while the copy is on, at most `ARMOR_INGEST_RECORD_DOWNLOADS_PER_HOUR` times an hour, and every download is written in the audit trail. Studio shows all of this in System. The file is limited to `ARMOR_INGEST_RECORD_MAX_BYTES` and rotated through `ARMOR_INGEST_RECORD_FILES` files.
* `POST /api/v1/node-health` (ingest token) and the topic `armor/health/<node>` carry the `node_health` report every node sends about once a minute. `GET /api/v1/node-health` lists the latest report of each node with its status (`ok`, `warning`, or `stale` after three minutes), its warnings, the restarts of the last day, the levels it judges by and the nodes it knows but that sent no report; `GET /api/v1/node-health/<id>` adds the history of its memory and signal (120 reports) and its restart log; `DELETE` (administrator) forgets a node. The latest reports and the restart logs are kept in `node-health.json` and survive a restart.
* The server judges, the node only tells. Four warnings reach the alarm centre for every node, and three more for radar nodes (see below) (as warnings, never told outside the consoles): `node_low_memory` (under 30 KB of heap, cleared at 40 KB; or, when the node tells its internal memory on its own - `heap_internal_free`, `heap_internal_min`, `heap_internal_largest`, with `psram_free` for the external RAM -, under 40 KB of it, cleared at 48 KB, or no free block of 8 KB; or a task short of stack), `node_frequent_resets` (three restarts in a day, or a crash in the last hour), `node_link_flapping` (three connections to the broker in 15 minutes, or the link down in two of the last six reports) and `node_weak_signal` (-80 dBm or worse in three reports in a row). A restart is seen when the uptime or the count of connections goes back.
* **Controlling a node from Studio and the phone:** `POST /api/v1/nodes/{id}/control` gives ONE order to ONE node and `POST /api/v1/nodes/control` gives the same order to every node that has reported lately; `GET /api/v1/nodes/control/operations` and `/{id}` list what was ordered in the last weeks, with a line per node. The operations are `restart`, `pause`, `resume`, `standby`, `identify`, `diagnostics`, `maintenance_on` and `maintenance_off`; there is no operation that erases a node's settings or credentials, none that puts it to deep sleep and none that sets a wake timer. Every route is for an administrator who proved themselves again a moment ago (`elevation_required` otherwise, from inside the house too); the body is `{operation, confirm?, duration_s?}` (and `mode` `now`|`rolling` for all nodes, rolling only for a restart). For `restart`, `pause` and `standby` `confirm` is the node's id typed again, or the word `RESTART`, `PAUSE` or `STANDBY` for all nodes. `duration_s` is for `pause` (60 to 3600, 3600 when absent), `identify` (5 to 300, 30) and `maintenance_on` (60 to 28800, 3600). Answers: 202 with the operation; 400 `invalid_request`; 403; 404 `unknown_node`; 409 `busy` (an order for that node is under way), `node_unavailable` (no report lately), `no_nodes` or `already_in_state`; 429 `rate_limited` (a restart at most once a minute per node, ten orders a minute altogether); 503 `mqtt_unavailable`. Only a node that reports its health can be ordered: the server and the CM5 are not nodes.
* **Planned maintenance, one window per node:** a node about to go quiet on purpose (a restart, an update, an upload, a pause, a standby) publishes the retained `node_maintenance` message to `armor/control/<node>/maintenance` (and `active: false`, retained too, when it is back); the server also reads the retained message when it starts. The operator's `maintenance_on` and the node's own announcement are ONE window: while either is in force the node is expected offline, so its offline alerts and the tamper inference are held back; the later end wins. What a node announces is bounded by the server: the time the node expects or `ARMOR_NODE_MAINTENANCE_MAX_S` (60 to 3600, default 600), whichever is shorter, a repeated announcement of the same reason adds nothing and a stretch of announcements ends at three times the bound; an operator window keeps the duration it was given (up to 8 hours). A node that returns (it says `active: false`, or reports a lower uptime) closes its own window. When the time passes and the node never came back, the node counts as offline again, the alerts resume and the history records `maintenance_expired` (`maintenance_started` and `maintenance_ended` mark a window the node announced). `GET /api/v1/nodes/maintenance` (any signed-in user) lists the windows in force with `source` (`node`, `operator` or `both`), `reason`, `expires_in_s` and `requested_by`; `GET /api/v1/node-health` carries the same in the `control` object (`maintenance`, `maintenance_until_s`, `window`). The windows survive a restart of the server.
* **How an order reaches a node:** for each node the server publishes an `arm` (`node_control_command`) to `armor/control/<node>/command`, waits for the node's answer on `armor/control/<node>/result` with a one-time token (30 seconds, bound to the operation) and executes with that token; the order is never retained and never goes to the broadcast topic `armor/control/all/command` except an arm. The token never leaves the server: it is not in a response, the history, the audit trail, a log or the file `node_control.json` where the operations are kept. A rolling restart gives each node a place (`slot`): sorted by id inside its family, the families in the order radar, solar, electrical, wall panel and the alarm panels last, the node waiting its place times thirty seconds. A line goes `pending`, `armed`, `sent`, then `acknowledged` (the node said it is restarting) and `offline` and `back` (its first report with a new uptime) for a restart, or `applied` (with the node's `state`) for the others, or `refused` (with the node's reason: `busy_update`, `busy_upload`, `busy_slot_copy`, `busy_battery`, `rate_limited`, `already_in_state` ...), `no_answer` or `not_back`.
* **What it leaves in the system:** each step is a `system` event of the history (category `node`; `control_requested`, `control_acknowledged`, `control_applied`, `control_refused`, `control_back` and `control_lost`, with the person, the node, the firmware and the operation in `profile`), the audit trail says who ordered what from where, `GET /api/v1/node-health` carries a `control` object per node (`state` running, paused or standby; `maintenance`; and, when known, `since_ms`, `by`, `until_s`, `maintenance_until_s`; `source` says whether the node reported it or the server remembers it from the orders), and while a node is in maintenance or a restart that was ordered is under way the alarms and the notifications about its silence are held back (they come back if the node is still silent when that ends). The broker lets only the server publish orders.
* **Diagnostics of a node (administrators):** `POST /api/v1/nodes/{id}/control` with `{"operation":"diagnostics","detail":"package"}` (or `"log"`) asks ONE node for its diagnostic package - memory, the tasks with the least stack, why it last started, the versions, the allowed part of its settings, the summary of its core dump and the newest log, never a secret - or for its log alone; the node delivers one at most every fifteen seconds. The server reads the package member by member (a member a node adds on its own is refused, never copied), keeps the latest package and the latest log of each node **in memory only** (a restart of the server forgets them) and shows them to administrators: `GET /api/v1/nodes/{id}/diagnostics`, and as a file `GET /api/v1/nodes/{id}/diagnostics/package?download=1` and `.../log?download=1` (each download is in the audit trail). The line of the operation says `delivered` (`package` or `log`) and does not copy the package.
* **The sign-in limit of a node (administrators):** `POST /api/v1/admin/nodes/settings` with `{node_id, address, panel_user, panel_password}` (the address is a private IPv4 of the node) signs in to the node's own panel with the login given (used once, never kept, and the audit line `admin.node.configure` carries only the new limit) and reads `system.login_limit_per_minute`, the wrong passwords per minute the node lets through before it locks sign-in for everyone (30 by default, 0 for no global limit, at most 120). With `login_limit_per_minute` in the body it also writes the new value through the node's own configuration route. The answer is `{ok, written, why, login_limit_per_minute}`; `why` says what failed (`panel_login_refused`, `panel_not_reachable`...) and `written` is true when the value was changed. Studio has a button for it on every node of its lists.
* **A firmware image goes only to a node of its board:** when the file name of an uploaded image says a board (`armor_<kind>-<board>.bin`) and the node reports another, that node fails with `wrong_board` before anything is sent to it; a node of another kind than the job fails with `wrong_node_kind`. Studio explains both in the eight languages.
* **Read-only diagnostic tokens:** `POST /api/v1/diagnostics/tokens` (an administrator who proved themselves again a moment ago) issues a token for one to sixteen nodes, for 300 seconds to 24 hours (two hours by default); the secret (`armor-diag-` and 43 characters) is in that answer and nowhere else - the server keeps only its SHA-256 in `diagnostic_tokens.json`, the list `GET /api/v1/diagnostics/tokens` never shows a secret or a hash, and `DELETE /api/v1/diagnostics/tokens/{id}` revokes it at once. At most twenty are active at a time, and what ended stays in the list for a week. A token (`Authorization: Bearer armor-diag-...`) reads, with GET and nothing else, `/api/v1/diagnostics/nodes` (the nodes it covers), `/nodes/{id}` (the health, the history of the memory and the log of restarts, with the last error washed and without the name of the person who last ordered the node), `/nodes/{id}/package` and `/nodes/{id}/log`; everything it reads is washed a second time of anything that looks like a credential. It cannot order anything, read another node or anything else of the house, issue or revoke a token, or reach a node's panel: on any other route it is no credential. Every refusal of an unknown, expired or revoked secret is the same 401 (the audit trail tells which, for a token that exists), a node outside the token is a 403, a token is held back after thirty requests a minute, and an address that has been refused twenty times in a minute is held back whatever it holds. The audit trail and the History record the issue, the revocation, the first use (and one use in ten minutes after that) and every refusal; the secret is in neither. Leaking one gives the finder the health and the logs of those nodes until it expires or is revoked, and nothing more (see the threat model of ARMOR-DOCS).
* **Radar nodes and their sensors:** the health report of a radar node carries its sensors (model, state, firmware, whether the sensor's own Bluetooth is open) and the facts of its perimeter engine; an open sensor Bluetooth raises the warning `node_sensor_bluetooth_open` (and a covered radar `node_radar_masked`, a suspected Wi-Fi jam `node_wifi_jam`). A node that starts after a crash, a watchdog, an out-of-memory or a restart of its own guard says so once (`boot`): the server keeps it in the node's log of restarts and writes `dirty_boot` in the History. The events of the node's own perimeter engine arrive on `armor/radar/<node>/events` (the `radar_event` message; a repeat of the same start and sequence number is kept once), `GET /api/v1/radar/events?node=<id>&limit=<n>` lists the newest (any signed-in user), and the History records the sensors' Bluetooth (`sensor_bluetooth_open`, `sensor_bluetooth_closed`) and the events that matter by their word (`radar_event`, with the event in `profile`: masking, jam, tripwire, loitering, path violation, serial bridge); a zone taken or left stays in the node's list only. The broker has to let the node write its own `armor/radar/<node>/events` and the server read them (`mqtt_identity.sh radar-events <node>` in ARMOR-DEVOPS).
* `GET`/`PUT /api/v1/alarm/profiles` keep the arming modes (`arm-profiles.json`): at most eight, `away` and `stay` always there with their own base, the list replaced as a whole with a revision (a conflict is a 409). `POST /api/v1/alarm/command` accepts `profile` (the id) on an arm; the whole profile goes inside the command to the node, only if the node's state says `arm_profiles: true` (`profiles_unsupported` otherwise), and the base must be the mode. The profile's `notify` decides the severity of the alarm a sounding panel raises: `urgent` is critical (escalated), `normal` is high. An arm without a profile is the command it always was.
* `GET`/`PUT /api/v1/alarm/modes` keep the arming modes of the server (away, home, night: what each defends, the exit and entry delays and an optional timetable; `arming-modes.json`), and `POST /api/v1/mode` takes `away`, `home`, `night` and `confirm_unassigned` besides `armed` and `disarmed`. All of it is off until `alarm.arming_modes` is turned on, and different from the arming profiles above (those say what a panel does when it is armed): see [ARMING_MODES.md](ARMING_MODES.md).

* The history also records the clients that connect and the system itself. `GET /api/v1/history` leaves the `connection` and `system` events out unless `type=connection`, `type=system`, one of their filters (`kind`, `client`, `category`, `user`) or `all=1` is given, so a client that only knows the older events never meets them. A `connection` event says that a client of a kind (`studio`, `android`, `node`, `voice`, `other`: what the client says in `X-Armor-Client: <kind>/<version>`, else what its user agent shows) was first seen, signed in, was refused (with a wrong password or a wrong code of the second factor), signed out, or had its session ended or expired; the name typed in a refused sign-in is kept only when it is the name of a real account. A `system` event uses a fixed vocabulary (nodes that appear, come back, change firmware or disappear; the broker link; settings changed, by whom and in which area, never the values; services; updates; the alarm armed, disarmed or silenced, with the arming profile) and has no free text. `GET /api/v1/history/connections` lists every client with when it was first and last seen and its open sessions. The schemas are `connection_event`, `system_event` and `connection_client` in ARMOR-COMMON.
